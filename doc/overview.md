*# LiNO Project Framework Overview

This repository implements a Light-inspired Neural Operator (LiNO) framework for learning solution operators of parametric partial differential equations (PDEs). The codebase is organized as a compact experimental system that prepares PDE datasets, trains neural-operator models, saves reproducible experiment artifacts, and evaluates checkpoints with visual and temporal-error analysis.

## 1. Framework at a Glance

The project is organized as a benchmark-oriented PDE operator-learning pipeline. Raw PDE data enters through the dataset layer, flows through shared preprocessing, is consumed by a LiNO model during training, and is decoded again during evaluation.

At a high level, the system has five layers:

1. User scripts
2. Experiment entrypoints
3. Dataset and preprocessing layer
4. Model layer
5. Training, evaluation, and output layer

Each layer has a distinct responsibility:

- **User scripts** expose convenient commands for common workflows.
- **Experiment entrypoints** define benchmark-specific training behavior.
- **Dataset modules** convert raw PDE data into normalized tensors.
- **Model modules** define the shared LiNO neural-operator backbone.
- **Training, evaluation, and output modules** manage reproducible runs, checkpoints, logging, and result artifacts.

The core design principle is to keep benchmark-specific logic at the edges. Data-format details and defaults belong in benchmark entrypoints, while the LiNO backbone and preprocessing utilities remain reusable.

## 3. Standard Workflow

The typical workflow is:

1. Download or place the dataset.
2. Run a training script.
3. Build training and validation tensors.
4. Train the LiNO model.
5. Save configuration, logs, and checkpoints.
6. Run an evaluation script.
7. Save prediction figures or error curves.

Training produces a run directory containing configuration, logs, and checkpoints. Evaluation consumes a checkpoint and produces visualizations or temporal-error summaries. This makes the workflow checkpoint-centered: each trained run stores enough metadata to reconstruct the model and decode predictions.

## 4. System Components

### Command Layer

The `scripts/` folder provides user-facing commands. These scripts hide working-directory details and invoke the corresponding Python entrypoints under `src/`.

They cover three task groups:

- dataset download
- model training
- model evaluation

For example, a training script changes into `src/` and launches the corresponding benchmark entrypoint. An evaluation script selects a checkpoint under `outputs/` and runs the shared evaluation program. These scripts are intentionally thin; the main logic stays in Python.

### Experiment Layer

The repository includes separate training entrypoints for the supported PDE benchmarks:

- Burgers1D
- Darcy2D
- Navier-Stokes2D

These entrypoints handle experiment-level concerns: command-line arguments, dataset choice, model configuration, optimizer settings, validation cadence, logging, and checkpoint paths. They follow a common pattern:

1. Parse experiment configuration.
2. Set the random seed.
3. Create the output directory.
4. Build dataset loaders.
5. Initialize the model.
6. Train and validate.
7. Save the latest and best checkpoints.

Burgers and Darcy are direct operator-learning tasks: the model maps one input field to one output field. Navier-Stokes is a time-dependent autoregressive task: the model predicts future frames step by step and feeds predictions back into the input history. This is the main workflow difference between the benchmarks.

### Data Layer

The data layer converts raw MATLAB files into tensors ready for neural-operator training. It isolates file-format and benchmark-specific details from the rest of the training stack.

It handles:

- `.mat` file loading
- extraction of benchmark-specific arrays
- optional spatial downsampling
- train/validation splitting
- coordinate-channel construction
- input and target normalization
- wrapping tensors into PyTorch datasets

The framework uses a channel-last tensor convention:

| Data Type | Tensor Layout |
| --- | --- |
| 1D data | `[batch, spatial_points, channels]` |
| 2D data | `[batch, height, width, channels]` |

This convention is consistent across datasets, models, training, and evaluation, which minimizes shape-conversion code between modules.

### Model Layer

The model layer defines the Light-inspired Neural Operator. Conceptually, the model has three stages:

1. **Lifting** maps raw input channels into latent features.
2. **Stacked light-evolution blocks** perform the main operator learning.
3. **Projection** maps latent features back to the target physical field.

Each light-evolution block combines three branches:

- **reflection**: local transformation of latent features
- **refraction**: adaptive rescaling of latent components
- **scattering**: spatial propagation of information

The block learns to combine these branches through a small gating mechanism, separating local feature processing from spatial communication.

The scattering component has two implementations: a full pairwise version for direct spatial-kernel modeling, and an efficient version that combines linearized global propagation with local diffusion. The efficient version is the default for larger grids, while the full version is useful for smaller grids and ablation studies.

### Training Layer

Training uses standard PyTorch components: mini-batch data loading, AdamW optimization, learning-rate scheduling, gradient clipping, epoch-wise validation, and checkpoint saving.

Each checkpoint stores both the model state and experiment context, including optimizer state, scheduler state, command-line arguments, validation metrics, and input/output normalizers. This makes evaluation reproducible, because the evaluator can reconstruct the model and decode outputs from the checkpoint alone.

### Evaluation Layer

Evaluation is checkpoint-driven. The evaluator loads a checkpoint, rebuilds the dataset split, restores the model and normalizers, selects validation samples, predicts outputs, decodes normalized results back to physical scale, and saves figures.

For time-dependent Navier-Stokes experiments, evaluation performs the same autoregressive rollout used during training. A separate temporal-error evaluator measures how rollout error evolves over time.

## 5. Data Flow

The end-to-end data flow is:

1. Raw PDE data is loaded from benchmark files.
2. A benchmark-specific loader extracts relevant fields.
3. Shared preprocessing applies resizing, splitting, coordinate channels, and normalization.
4. Normalized train and validation tensors are wrapped in data loaders.
5. The LiNO model consumes mini-batches during training.
6. Losses are computed and model parameters are updated.
7. Checkpoints store the trained model and experiment context.
8. Evaluation decodes predictions back to physical scale.

The key design choice is that benchmark-specific loaders handle only dataset details, while shared preprocessing remains common. Once tensors reach the training loop, the benchmarks follow a mostly uniform interface.

For stationary problems such as Burgers and Darcy, input-output pairs are constructed directly. For Navier-Stokes, the loader first splits a trajectory into history and future frames, and training performs autoregressive rollout over the future window.

## 6. Experiment Outputs

Experiment outputs are stored under `outputs/`. A typical training run saves:

| Artifact | Purpose |
| --- | --- |
| `outputs/<experiment_name>/config.json` | Saved experiment configuration |
| `outputs/<experiment_name>/logs/` | Training and validation logs |
| `outputs/<experiment_name>/ckpts/last_model.pt` | Most recent checkpoint |
| `outputs/<experiment_name>/ckpts/best_model.pt` | Best validation checkpoint |

Evaluation may add prediction figures, comparison plots, or temporal-error summaries. These files are generated artifacts rather than source code. The checkpoint and its saved configuration provide the metadata required for later reproduction and analysis.
